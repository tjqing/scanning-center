## 1. SSH 私钥：从前端粘贴改为「查库 → 加密 → 写入代码库」

### 1.1 背景与现状

| 项 | 说明 |
|----|------|
| 原流程 | 前端粘贴私钥 → 接口传 `secret` → 后端 `SecretCodec.encrypt` → 写入 `repository_catalog.encrypted_secret` |
| 现状 | 前端已去掉私钥录入；保存代码库时不传 `secret` |
| 当前兜底 | `applyGitCredential`：有明文则加密；编辑保留原密文；否则 `findSharedSshCredential` **直接拷贝兄弟行密文**（不解密、不重新加密） |
| 拉取解密 | Git 克隆时 `decryptSecret` → `SecretCodec.decrypt`（与「保存入库」分开，一般不必改） |
| 前端 | **无需再改**（粘贴入口已去掉） |

### 1.2 目标形态

1. 从**统一凭据源**（独立表 / 配置库 / 现有某张密钥表，待定）查询 SSH 私钥（明文或已约定格式）。
2. 调用 `SecretCodec.encrypt` 加密。
3. 写入当前代码库记录的 `encrypted_secret`。
4. Git 拉取继续走 `decryptSecret`，无需前端再粘贴。

### 1.3 涉及文件与修改方式

| 优先级 | 文件 | 改什么 | 怎么改 |
|--------|------|--------|--------|
| P0 | `src/main/java/com/scan/center/service/RepositoryCatalogService.java` | **主改点** `applyGitCredential` | 去掉「拷贝兄弟行密文」主路径；改为：查统一凭据源 →（如需）`sanitizeSshPrivateKey` → `secretCodec.encrypt` → `value.setEncryptedSecret(...)`。 |
| P0 | 同上 `validate` 中凭据相关校验 | 60012 错误语义 | 改为校验「统一凭据源是否可查到可用私钥」。 |
| P1 | 新建 Mapper / 表 或外部 Client | 统一凭据源 | 提供查询可用私钥的方法，仅在 `applyGitCredential` 内调用。 |
| P1 | `RepositoryCatalogMapper` + XML | `findSharedSshCredential` | 切换完成后可废弃。 |
| — | `SecretCodec` / `SourceWorkspaceService` | 加解密、Git 拉取 | **一般不改**。 |
| — | 前端 | — | **无需修改**。 |

### 1.4 建议实施步骤

1. 定统一凭据源与运维导入方式（非业务前端）。
2. 只改 `applyGitCredential`（及配套 `validate`），验证新建后可 `decryptSecret` 还原。
3. 跑通一次 Git 扫描源克隆。
4. 下线 `findSharedSshCredential`。
5. 更新本文档状态为「已完成」。

### 1.5 定位口令

- 方法名：`applyGitCredential`
- 或：`TODO 后期改本方法：从统一凭据源查询`

## 2. 应用列表 / 版本列表：前端挡板改为「后端调第三方接口」

### 2.1 背景与现状

| 项 | 说明 |
|----|------|
| 前端应用 | `web/src/constants/applications.js` 写死 `APPLICATIONS` / `CONCRETE_APPLICATIONS` |
| 前端版本 | `web/src/constants/mdVersions.js` 写死 `MD_VERSION_MOCK`，`loadMdVersions` 返回挡板 Promise |
| 使用页面 | 筛选/表单多处：`TaskView`、`IssueView`、`RepositoryView`、`RepositoryCatalogView`、`UserView` 等 |
| 后端应用校验 | `ApplicationOptions` 同样是本地常量白名单，与前端列表需保持一致 |
| 后端版本 | 已有 MD 版本查询雏形：`RepositoryController` `GET /repositories/md/versions` → `RepositoryService.mdVersions` → `MdDocumentHttpClient.versions`（按文档类型 + 应用调第三方）；表单挡板尚未统一走该链路 |

### 2.2 目标形态

1. **应用列表**：后端提供统一 API（内部调第三方 / 主数据），前端下拉全部改调该 API，去掉本地写死列表（或仅作离线兜底）。
2. **版本列表**：后端提供统一 API（可复用/扩展现有 `md/versions`，或新建「按应用查版本」通用接口），`loadMdVersions` 改为请求后端；筛选栏与表单共用同一数据源。
3. 后端校验（`ApplicationOptions.contains`、版本是否合法）改为与第三方结果一致，避免前后端两套硬编码漂移。

### 2.3 涉及文件与修改方式

| 优先级 | 文件 | 改什么 | 怎么改 |
|--------|------|--------|--------|
| P0 | 新建或扩展 Controller/Service（如 `MetaController` / 扩 `RepositoryController`） | 应用列表 API、版本列表 API | 例：`GET /api/v1/meta/applications`、`GET /api/v1/meta/versions?application=&documentType=`；内部调第三方，统一返回 `{ code/label }` 或现有 `versionNo`+`label` 结构。 |
| P0 | 新建 `XxxHttpClient` 或扩展 `MdDocumentHttpClient` | 第三方调用 | 应用列表、版本列表分别封装；超时/空结果/降级策略产品定。 |
| P0 | `web/src/constants/mdVersions.js` | `loadMdVersions` | **主改点（前端）**：改为 `request.get` 调后端版本 API；可保留 `MD_VERSION_MOCK` 作开发兜底，正式环境走接口。 |
| P0 | `web/src/constants/applications.js` | 应用列表 | 改为 `loadApplications()` 调后端；或新建 `api/meta.js`，各页 `created`/`mounted` 拉取后赋给下拉。`CONCRETE_APPLICATIONS` 由接口结果过滤 `ALL` 得到。 |
| P1 | `web/src/views/*`（Task/Issue/Repository/Catalog/User） | 下拉数据源 | 把直接绑 `APPLICATIONS` / `MD_VERSION_MOCK` 改为绑异步加载结果；筛选栏与表单共用同一 load 方法。 |
| P1 | `src/main/java/com/scan/center/common/ApplicationOptions.java` | 本地白名单 | 改为缓存第三方应用列表，或校验时实时/短缓存查询；避免与前端再各维护一份。 |
| P1 | `RepositoryService.mdVersions` / `MdDocumentHttpClient` | 已有版本接口 | 与通用版本 API 对齐：返回结构补 `label`（若第三方只有 versionNo，后端组装展示名）；筛选页也可复用，不必只服务 MD。 |
| P2 | `application.yml` | 第三方 URL | 配置应用列表 URL、版本列表 URL（可与现有 `scan-center.md-api.*.versions-url` 合并规划）。 |

### 2.4 建议实施步骤

1. 与第三方定应用列表、版本列表接口契约（字段、是否按应用过滤版本、是否含 `ALL`）。
2. 后端先落地两个只读 API + Client，Postman 验通。
3. 改 `mdVersions.js` / `applications.js`（或统一 meta API 模块），一页试点（建议 `RepositoryCatalogView`）。
4. 其余 Vue 页批量替换写死常量。
5. 后端 `ApplicationOptions` 与保存校验切到同一数据源。
6. 去掉或降级挡板常量，更新本文档状态。

## 3. 统一认证 / SSO（后续）

### 3.1 现状（已落地开发态）

| 项 | 说明 |
|----|------|
| 登录 | 用户名 + 密码；密码存 `password_hash`（SHA-256+pepper）；默认密码 `kzxf-123456` |
| 会话 | `localStorage` key `scan-center-user`（含 `expiresAt`，登录起 8h 绝对过期）；请求头 `X-User-Id` |
| 后端 | `OperatorInterceptor` → `OperatorContext`；写操作人用 `AuditOperator.userId()` / `userName()` |
| 退出 | 清本地会话 + `POST /api/v1/auth/logout`（服务端无状态） |
| 路由 | 未登录进登录页；`requiresAdmin` 非管理员拦截 |

### 3.2 目标

接入公司统一认证（SSO / OAuth / 网关 Token），替换开发态选用户登录。

### 3.3 涉及文件与修改方式

| 优先级 | 文件 | 改什么 | 怎么改 |
|--------|------|--------|--------|
| P0 | `AuthController` / `AuthService` | 登录实现 | 改为校验统一 Token / 换票；`login-users` 可下线 |
| P0 | `OperatorInterceptor` | 身份解析 | 从网关头 / Cookie / JWT 解析用户，映射到 `system_user`（按 `externalUserId` 或用户名） |
| P0 | `web/src/views/LoginView.vue`、`utils/auth.js` | 登录页与会话 | 跳转 SSO 或消费回调 Token；本地仍可缓存用户简要信息 |
| P1 | `web/src/utils/request.js` | 请求头 | `X-User-Id` 改为 `Authorization` 等正式头 |
| — | 业务 Service | 操作人写入 | **一般不改**（继续 `AuditOperator.userId()`） |

### 3.4 定位口令

- `AuthController`、`OperatorContext`、`X-User-Id`
- 前端：`utils/auth.js`、`LoginView.vue`
