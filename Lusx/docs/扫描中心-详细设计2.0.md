# 第一章 总体概述

**业务背景**：随着研发代码量与业务文档规模不断增长，敏感信息（密钥、凭据、账号）、高危配置及违规内容靠人工评审已难以覆盖，漏检风险高、效率低。单一关键字/正则扫描无法理解上下文、误报率高，纯 AI 扫描又成本高、结果不可控。扫描中心作为统一的**代码与文档安全扫描平台**，采用「普通规则（NORMAL）+ AI 大模型」双通道互补的闭环方案：普通规则负责高吞吐基线扫描兜底，AI 结合提示词做语义研判、降低误报，最终产出问题清单交由业务人员确认、整改与忽略。

**功能模块实现功能**：系统主要分为七大功能模块，各自实现功能如下：

1. 规则维护：管理普通规则（关键字/正则、风险等级、文件类型与排除项）与 AI 规则（提示词内容），支持新增、编辑、复制、启停与删除。
2. 扫描源维护：维护 Git 仓库、ZIP 上传、数据库文档三类扫描来源，含目录与用户授权关系。
3. 扫描任务与扫描结果：选择扫描源与多规则创建扫描任务，执行时固化规则与清单快照，支持异步执行、进度展示、暂停、续扫与中止；并按任务汇总扫描结果（文件数、风险分级）。
4. 扫描问题：展示问题清单并支持按风险/状态过滤、处理与导出。
5. 模型配置：维护大模型凭证、提示词模板与 Token 重试次数。
6. 用户管理：管理系统账号及其启停。
7. 代码库维护：维护代码库目录（名称、地址、所属应用）及其启停，作为扫描源与用户授权的基础数据来源。

整体采用前后端分离，同步管理、异步执行，问题落库后由人工闭环处理。

## 2.1 规则维护

### 2.1.1 详细设计

**功能定位**：维护扫描中心可执行的检查规则，支持普通规则（关键字/正则）与 AI 规则（两阶段提示词）两类，实现规则的查询、新增、编辑、复制、启停与删除。

**操作步骤（新增规则表单填写说明）**：

**步骤 1：填写规则编码（`ruleCode`）**

- 为本规则指定**全局唯一**的英文编码，便于在脚本、配置中引用。
- 仅允许字母、数字、下划线、短横线，≤64 字符，例如 `SECRET_AWS_ACCESS_KEY`、`PII_PHONE_NUMBER`。
- 注意：**不可包含中文、空格、点号、特殊符号**；与现有规则编码重复将保存失败。
- 与"规则名称"的区别：`ruleCode` 是程序内部引用的唯一标识，`ruleName` 用于界面列表展示。

**步骤 2：填写规则名称（`ruleName`）**

- 为规则填写一段描述性名称。
- ≤128 字符的文本，例如"检查代码中是否硬编码 AWS AccessKey"。

**步骤 3：选择规则类型（`ruleType`）**

- 明确规则采用机器匹配方式还是大模型语义研判方式。
- 怎么选：单选 `NORMAL`（普通） / `AI`。
- **区别**：
  - **普通（NORMAL）**：采用关键字/正则匹配，**不调用大模型**。执行效率高、资源消耗低，适用于大批量基线扫描，命中方式为字符串匹配。
  - **AI（AI）**：采用大模型语义研判，通过 `AiModelHttpClient` 调用。**必须配置检查规则与结果更新两段提示词**，能够理解上下文、降低误报率。
- 切换后续字段会联动变化：选 `NORMAL` 显示"匹配方式 / 匹配内容"；选 `AI` 显示"检查规则 / 结果更新"。

**步骤 4：选择可见范围（`visibility`）**

- 判断该规则是否需要开放给其他用户使用。
- 怎么选：单选 `PRIVATE`（私有） / `SHARED`（共享），默认 `PRIVATE`。
- **区别**：
  - **私有（PRIVATE）**：仅创建者可查看、编辑与使用。
  - **共享（SHARED）**：对系统所有用户可见、可选用于任务；用于推广组织级规范。

**步骤 5：选择扫描对象（`targetType`）**

- 明确规则作用的扫描对象类型。
- 怎么选：下拉 `ALL`（全部）/ `CODE`（代码）/ `DOCUMENT`（文档）。
- **区别**：
  - **全部（ALL）**：在代码扫描和文档扫描两类任务中都生效。
  - **代码（CODE）**：仅在以代码为扫描源（Git/ZIP 代码）的任务中生效。
  - **文档（DOCUMENT）**：仅在以文档为扫描源（数据库 / MD 文档）的任务中生效。

**步骤 6：选择风险等级（`riskLevel`）**

- 评估规则命中后所对应问题的严重程度。
- 怎么选：下拉 `HIGH`（高）/ `MEDIUM`（中）/ `LOW`（低）/ `INFO`（提示）。
- **区别**：
  - **HIGH（高）**：涉及硬编码密钥、隐私泄露等高风险场景，需优先处理。
  - **MEDIUM（中）**：存在明显违规但危害有限，例如日志中打印敏感字段。
  - **LOW（低）**：建议性整改项，例如注释不规范、存在可优化点。
  - **INFO（提示）**：仅作为信息提示，不强制处理。
- 所选等级将作为问题落库时的默认风险等级。

**步骤 7A：普通规则 — 选择匹配方式（`matchType`）**

- 仅在 `ruleType=NORMAL` 时出现。
- 怎么选：单选 `KEYWORD`（关键字） / `REGEX`（正则），默认 `KEYWORD`。
- **区别**：
  - **关键字（KEYWORD）**：将 `matchContent` 作为子串匹配，扫描时先按语言去除注释再匹配，配置简单。
  - **正则（REGEX）**：将 `matchContent` 作为正则表达式匹配，匹配能力更灵活（适用于邮箱、手机号、密钥模式等场景）；保存前需确保正则可编译。

**步骤 7B：普通规则 — 填写匹配内容（`matchContent`）**

- 仅在 `ruleType=NORMAL` 时出现。
- 
  - 关键字：填写待匹配的字符串，例如 `AKIA`、`password=`、`TODO-FIXME`。
  - 正则：填写标准正则表达式，例如 `(?i)bearer\s+[A-Za-z0-9-_=]{20,}`（大小写是否敏感由 `caseSensitive` 决定）。
- 说明：扫描器会**先按语言去除注释，再执行匹配**，以避免注释内容造成误报。
- 长度：≤20000。

**步骤 7C：AI 规则 — 填写检查规则（`checkRuleContent`）**

- 仅在 `ruleType=AI` 时出现。
- 两阶段提示词中的**第一阶段**，用于引导大模型识别文件中可能存在问题的位置，≤30000。
- 示例：要求模型依据 `checkRuleContent` 与文件内容，输出 JSON，描述初步命中信息（位置、怀疑理由）。

**步骤 7D：AI 规则 — 填写结果更新（`resultUpdateContent`）**

- 仅在 `ruleType=AI` 时出现。
- 两阶段提示词中的**第二阶段**，用于引导大模型将第一阶段的初步结果整理为最终问题列表，≤30000。
- 说明：两段提示词均非空方可保存；模型最终输出按 `issues[]` 解析为 `scan_issue` 落库。

**步骤 8：填写文件类型（`fileTypes`）**

- 明确该规则生效的文件扩展名范围。
- 英文逗号分隔，≤500，例如 `java,js,ts,md,yml`；每项格式 `^[A-Za-z0-9]+(?:[._+-][A-Za-z0-9]+)*$`，**不允许中文逗号、分号及空项**。
- 留空：表示对所有文件类型生效。

**步骤 9：填写排除目录（`excludePatterns`）**

- 列出扫描时需要跳过的目录名（如构建产物、依赖目录）。
- 英文逗号分隔，≤1000，例如 `target,node_modules,dist,.git`；每项**不允许含中文逗号、分号或空白**。
- 留空：表示不进行目录排除。

**步骤 10：填写问题说明（`issueDescription`）**

- 填写规则命中后展示给复核人员的问题描述。
- ≤1000，例如"检测到硬编码的 AWS AccessKey，存在密钥泄露风险"。
- 留空：落库时该字段为空。

**步骤 11：填写整改建议（`suggestion`）**

- 填写提供给开发者的修复指引。
- ≤1000，例如"请改用环境变量或配置中心读取密钥，并轮转已泄露的 AccessKey"。
- 留空：落库时该字段为空。

**步骤 12：选择启用（`enabled`）**

- 决定该规则保存后是否立即参与任务扫描。
- 怎么选：开关，开（true）/ 关（false）；新增默认开，**复制生成的副本默认关**，以避免未经验证即启用造成误报。
- 与列表"启停"开关的区别：列表中的 Switch 通过 `PUT /rules/{id}/status` 即时切换；本处开关仅控制"保存后是否启用"。

**步骤 13：保存**

- 点击"保存"：前端先执行格式校验（编码、逗号列表、正则），通过后调用 `POST /api/v1/rules`，由 `RuleService.create` 执行后端二次校验，落库成功返回新规则 ID。
- 已有任务快照不受影响：保存成功后提示"保存成功；已有任务快照不会自动变化"，即历史任务使用建任务时的规则快照，**修改规则不回溯影响历史任务**。

**步骤 14：复制 / 删除 / 启停（列表行操作）**

- **复制（`POST /rules/{id}/copies`）**：生成规则副本，`ruleCode` 自动追加 `_COPY_{时间戳}`、`ruleName` 追加 `-副本`，副本默认停用，避免误启用。
- **删除（`DELETE /rules/{id}`）**：**逻辑删除**（软删）；若该规则已被任一任务引用（`countTaskReference > 0`），拒绝删除并提示"只能停用"。
- **启停（`PUT /rules/{id}/status?enabled=...`）**：列表 Switch 即时调用，仅切换 `enabled`，不修改规则内容。

**处理逻辑小结**：

1. **分页查询**：支持 `keyword`（规则名称或编码模糊）、`type`（规则类型）、`enabled`（启用状态）过滤；页码从 1 起，`pageSize` 限制在 1~100。
2. **新增 / 编辑**：公共校验通过后落库；`visibility` 缺省为 `PRIVATE`，`enabled` 缺省为 `true`；写入操作人审计字段（开发态 `AuditOperator`，默认用户 ID 1）。
3. **复制**：基于源规则生成副本，`ruleCode` 追加 `_COPY_{时间戳}`，`ruleName` 追加 `-副本`，新副本默认 `enabled=false`。
4. **删除**：**逻辑删除**（软删）；若规则已被任务引用（`countTaskReference > 0`），则拒绝删除并提示"只能停用"。
5. **启停**：直接更新 `enabled` 状态，不改变规则内容。

### 2.1.2 重要接口

#### 2.1.2.1 接口设计

规则是扫描中心执行扫描的依据，用于定义扫描对象与扫描方式。普通规则通过关键字或正则表达式定义匹配文本，AI 规则通过两阶段提示词实现语义研判；规则命中后按照风险等级生成问题记录，作为人工复核与整改的输入。创建任务时需选择多条规则，并将其内容固化为任务快照，确保历史任务的可追溯性。规则维护是平台扫描能力的基础入口。

#### 2.1.2.2 接口定义

接口清单：

| 功能 | 方法 | 路径 | 请求参数 | 请求体 | 响应 data | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| 分页查询 | GET | `/api/v1/rules` | `keyword`,`type`,`enabled`,`pageNum=1`,`pageSize=20` | 无 | `PageResult<ScanRule>` | 分页条件查询 |
| 详情 | GET | `/api/v1/rules/{id}` | 路径 `id` | 无 | `ScanRule` | 不存在抛 `10001` |
| 新增 | POST | `/api/v1/rules` | 无 | `RuleSaveDTO` | `Long`（新 ID） | 创建规则 |
| 编辑 | PUT | `/api/v1/rules/{id}` | 路径 `id` | `RuleSaveDTO` | `null` | 更新规则 |
| 删除 | DELETE | `/api/v1/rules/{id}` | 路径 `id` | 无 | `null` | 逻辑删除；被引用抛 `10002` |
| 复制 | POST | `/api/v1/rules/{id}/copies` | 路径 `id` | 无 | `Long`（新 ID） | 生成副本 |
| 启停 | PUT | `/api/v1/rules/{id}/status` | 路径 `id`、查询 `enabled` | 无 | `null` | 更新启用状态 |

## 2.2 扫描源维护

### 2.2.1 详细设计

**功能定位**：维护扫描中心可供任务使用的扫描来源。支持三种获取方式——`GIT`（Git 拉取）、`UPLOAD`（ZIP 上传）、`HTTP`（MD 文档获取）；实现扫描源的查询、新增、编辑、启停、删除、ZIP 上传与替换、MD 版本查询。

**核心概念**：

- **获取方式 `sourceType`**：`GIT` / `UPLOAD` / `HTTP`，决定扫描源数据的获取途径。
- **扫描内容 `scanSourceType`**：`CODE`（代码，Git/ZIP 拉取后为代码）/ `MD`（文档，HTTP 获取后为文档）。
- **GIT（Git 拉取）**：选择一个或多个有权访问的代码库（`repositoryCatalogIds`），输入统一拉取分支，系统以公用只读账号分别拉取。
- **UPLOAD（ZIP 上传）**：选择单个项目（`repositoryCatalogId`），上传一个 ZIP 包（≤50MB），用于单项目扫描。
- **HTTP（接口获取）**：选择应用与文档类型（概要设计.md / 详细设计.md），从独立配置的接口拉取指定 `YYYYMM` 版本文档。

**处理逻辑（新增扫描源）**：

1. 选择获取方式 `sourceType`，系统按类型走不同的字段配置与校验：
   - **GIT**：校验代码库非空、≤100 个、分支合法（`^[A-Za-z0-9._/-]{1,128}$` 且不含 `..`、不以 `/` 开头结尾）；自动装配多个项目的 Git 项目清单。
   - **UPLOAD**：校验已选单个项目；保存后需再上传 ZIP 文件。
   - **HTTP**：校验文档类型为 `OVERVIEW_DESIGN` / `DETAIL_DESIGN`、版本为 `\d{6}`（YYYYMM）且在接口返回范围内。
2. `scanSourceType` 由系统按类型自动设置（GIT/UPLOAD → `CODE`，HTTP → `MD`）。
3. `repositoryName` 按类型自动生成（如 `名称@分支`、`ZIP@项目名`、`详细设计.md-应用@YYYYMM`）。
4. `enabled` 缺省为 `true`，写入操作人审计字段。
5. 保存成功后，UPLOAD 类型需再调用上传接口补充 ZIP 文件。

**UPLOAD 类型校验**：仅 UPLOAD 允许上传；文件须为 `.zip` 且 ≤50MB；文件名安全化处理，存储用随机 UUID 文件名，避免路径穿越。

| UPLOAD ZIP | 新增时必须选择 ZIP 文件；`.zip` 扩展名、≤50MB |
| HTTP 文档类型 | 必须选择概要设计.md / 详细设计.md |
| HTTP 版本 | 版本必填，格式 `^\d{6}$`（YYYYMM） |

### 2.2.4 业务逻辑处理

业务逻辑处理按三种获取方式分别说明。

**目录结构总览（Linux 部署示例）**：

假设程序以 **JAR 运行在 `/opt/scanning-center`**（`scanning-center.jar` 所在目录即"运行目录"），配置 `scan-center.workspace-root=./data/workspace`、`scan-center.storage-root=./data/storage`（见 `application.yml`）。

相对配置项会**以运行目录为基准解析**成绝对路径（代码中通过 `Paths.get(...).toAbsolutePath().normalize()` 解析；生产建议直接配成 `/opt/scanning-center/data/workspace` 这类绝对路径）：

```
/opt/scanning-center/                       ← 运行目录（部署 jar 的位置）
├── scanning-center.jar                     ← 程序包
├── data/
│   ├── workspace/                          ← workspace-root（快照/内容落地根）
│   │   └── snapshots/                      ← snapshotRoot（任务快照内容根）
│   │       └── {snapshotId}/               ← 本次任务快照的 base 目录
│   │           ├── backup-{UUID}/          ← 本次拉取/解压/下载的临时落地目录
│   │           └── current/                ← 对外最终可用目录（backup 原子替换产物）
│   └── storage/                            ← storage-root（ZIP 上传包落盘根）
│       └── {storageKey}.zip                ← 用户上传的压缩包（未解压原包）
```

> **三种扫描源在 `current/` 下的内容形态**（`backup-{UUID}/` 内同构，仅临时）：
>
> **GIT（代码）** — 每个项目一个子目录（按 `safeDirectory(name)` 命名，重名追加 `-{id}`）：
> ```
> current/
> ├── project-a/            ← 项目A clone 出的仓库
> │   ├── src/ …
> │   └── pom.xml
> └── project-b/            ← 项目B（多项目扫描源支持多个）
>     └── src/ …
> ```
>
> **UPLOAD / ZIP（代码）** — 解压后的文件平铺于 `current/`（无额外一层目录）：
> ```
> current/
> ├── src/ …
> └── pom.xml
> ```
>
> **HTTP / MD（文档）** — `current/` 作为**版本名称目录**，下存「概要设计」与「详细设计」两篇 md 文档（`current` 由数据管理平台接口按所选版本落盘，示例版本目录名为 `2026年9月份版本`）：
> ```
> current/
> └── 2026年9月份版本/            ← 版本编号目录（按所选版本命名）
>     ├── 概要设计.md
>     └── 详细设计.md
> ```

- 三者关系：**`base = workspace-root/snapshots/{snapshotId}`**；`backup`、`current` 都在 `base` 之下；**ZIP 原始上传包**落在 `storage-root`（与快照内容目录是两套根，互不相混），解压后的代码才进 `current/`。
- 每个任务一个 `{snapshotId}` 目录，任务间互不干扰。同任务每次 `prepare` 都会新建 `backup-{UUID}` 重新拉取/解压/下载，再删除旧 `current` 后原子替换（当前为**全量拉取**，Git hash 增量复用见 2.2.4.1 Step 2 说明，尚未实现）。
- 三种扫描源**共用同一套 base 目录机制**：`prepare` 时 `prepareCode`（GIT/UPLOAD）或 `prepareMd`（HTTP）把内容写入 `backup`，校验含普通文件后整体原子替换为 `current`；后续清单遍历、逐单元扫描都以 `current` 为根。

> **磁盘清理（清盘）策略——当前未实现**：
>
> 当前已实现的清理仅限 `prepare` 内：失败时 `safeDelete(backup)` 删除本次临时目录、替换时 `deleteTree(current)` 删除旧 `current`。以下**清盘策略尚未实现**，需后续补充：
> - **快照目录回收**：任务删除（`TaskService.delete`）仅做数据库逻辑删除，`workspace/snapshots/{snapshotId}` 目录不随之清理，长期运行会持续占用磁盘。
> - **存储原文件回收**：`storage-root` 下的 ZIP/MD 原始上传包，在扫描源删除或替换文件时不清理旧 `storageKey` 文件，存在孤儿文件。
> - **`deleteSnapshot` 未生效**：`SourceWorkspaceService.deleteSnapshot` 已实现（越界校验 + `safeDelete`）但**无任何调用方**，为待接入的死代码。
> - **全局定时回收缺失**：无识别数据库未引用孤儿快照/文件、清理过期 `backup-{UUID}` 的定时任务（如 `@Scheduled`），需补充磁盘配额与保留策略。

#### 2.2.4.1 Git 拉取（GIT）

**处理流程**：

`RepositoryView` 前端保存 → `RepositoryController.create` → `RepositoryService.create` → `RepositoryService.prepare` → `prepareGit` → `RepositoryMapper.insert` → 写入 `code_repository` 表。



**Git 拉取执行细节（`SourceWorkspaceService`）**：

Git 扫描源真正落地代码库文件在**任务快照生成阶段**完成，由 `SourceWorkspaceService` 统一调度，按"准备目录 → 拉取前 hash 判定（复用或拉取） → 校验 → 原子替换"四步执行。

> **Git 私钥（访问令牌）来源**：
>
> - 用户的 Git 访问令牌（私钥）**存在 `code_repository` 表的 `encrypted_token` 字段**（加密存储，`username` 字段存仓库访问用户名；`schema-mysql.sql` 中 `code_repository.encrypted_token COMMENT '加密访问令牌'`）。
> - 建扫描源时前端提交用户名 + token，后端经 `SecretCodec.encrypt(token)` 加密后写入 `code_repository.encrypted_token`，库中**不存明文**。
> - 任务执行 `cloneRepository` 时，从 `code_repository` 读取该条记录的 `username` / `encrypted_token`，用 `SecretCodec.decrypt(encrypted_token)` 解密得到真实 token，组装 `UsernamePasswordCredentialsProvider(username, token)` 做 Git 认证。
> - **多项目地址与统一分支**：一个 Git 扫描源可配置**多个 Git 地址**（`code_repository.git_projects_json`，JSON 数组，每项含 `{id,name,url,application}`），拉取时按统一分支名 `code_repository.default_branch` 逐个 clone；认证凭证（`username` / `encrypted_token`）对同一扫描源下所有项目共用。

**Step 1：准备目录（`prepare(Long snapshotId, CodeRepository repository, String versionNo)`）**

- 计算三个关键目录，并对快照根做**越界校验**（`base.startsWith(snapshotRoot)`，防止路径穿越）：
  - `base` = `{workspace-root}/snapshots/{snapshotId}`
  - `backup` = `{base}/backup-{UUID}`（本次拉取写入的临时目录，UUID 随机生成避免并发冲突）
  - `current` = `{base}/current`（对外最终可用的代码目录）
- `Files.createDirectories(backup)` 创建备份目录。
- 按 `scanSourceType` 分派：
  - `CODE` → `prepareCode`
  - `MD` → `prepareMd`（走 HTTP 下载，与本场景无关）
- 拉取完成后调用 `containsRegularFile(backup)` 校验目录内**存在可扫描的普通文件**，否则抛"扫描源中没有可扫描文件"。
- 若已存在旧 `current`，先 `deleteTree(current)` 整目录删除，再 `Files.move(backup, current, ATOMIC_MOVE)` **原子替换**，返回 `current` 路径。
- 异常兜底：任一环节失败均 `safeDelete(backup)` 清理本次临时目录，再抛出 `30021`（"扫描源准备失败"）。

**Step 2：拉取前 hash 增量判定（`prepareCode` 内，GIT 源）**

> **说明**：hash 增量比对**当前未实现**，现行为每次全量 clone。以下为设计目标流程，**后期开发排期实现**。

- 依据 `sourceType` 分派：
  - `GIT` → `cloneRepositories(repository, target)`（走 git 拉取 / 复用）
  - `UPLOAD` → 校验 `storageKey` 非空且路径合法（`zip.startsWith(storageRoot)` 防越界），`ZipExtractor.extract(zip, target)` 解压
  - 其它 → 抛"CODE扫描源只支持Git或ZIP"。
- **操作集合**：分支判断使用字符串常量集合 `{"GIT","UPLOAD"}` 对照。

**Step 3：多项目增量处理（`cloneRepositories` + `cloneRepository`）**

`cloneRepositories(CodeRepository repository, Path target)`：

- 解析项目清单 `projects`：
  - 若 `gitProjectsJson` 为空 → 构造**单元素集合** `Collections.singletonList(legacyProject(repository))`（兼容旧数据）。
  - 否则 `json.readValue(gitProjectsJson, new TypeReference<List<GitProject>>(){})` 解析为 `List<GitProject>`。
  - 空集合 → 抛"Git扫描源未配置项目"。
- 使用集合 `Set<String> directories` 记录已占用目录名，避免重名覆盖：对每个项目取 `safeDirectory(name)`，若重名则追加 `-{project.id}`。
- **对每个项目先执行 hash 增量判定，再决定"复用"还是"拉取"**（见下方 hash 增量判定小节）：
  - **hash 相同（复用）**：跳过 `cloneRepository`，直接复用 `current` 下已存在的原代码目录。
  - **hash 不同（拉取）**：调用 `cloneRepository(url, defaultBranch, target.resolve(directory))` 拉取最新代码。
- **同步串行拉取（非并发）**：上述 `for` 循环对多个项目**逐个顺序 clone**（无 `parallelStream` / 线程池 / `CompletableFuture`）；`cloneRepository` 内 `command.call()` 为 JGit **同步阻塞**调用，clone 完一个才进入下一个。多项目间不并行，任务级并行仅体现在不同任务各占 `scan-center.worker-threads` 线程。

`cloneRepository(String url, String branch, Path target)`（JGit）：

- **工具包**：使用 **JGit**,纯 Java Git 库，库内嵌操作。
- 分支非空时 `setBranch(branch)`（`branch` 取扫描源统一分支 `repository.getDefaultBranch()`）。
- **认证**：从 `code_repository` 表读取当前扫描源的 `username` / `encrypted_token`，`SecretCodec.decrypt(encrypted_token)` 解密得到 token，注入 `UsernamePasswordCredentialsProvider(username, token)` 做认证；若该扫描源未配置私钥（`encrypted_token` 为空）则**匿名拉取**（公有仓库）。
- 构造 `CloneCommand`：`Git.cloneRepository().setURI(url).setDirectory(target.toFile())`，再 `command.call()` 执行 clone。

> **hash 增量判定（复用 / 拉取的决策点）**：
>
> 1. 拉取前检查 `current` 目录下是否已存在目标仓库目录（按 `safeDirectory(name)` 定位）。
> 2. 若**已存在**，读取本地 HEAD 提交的 hash（`git rev-parse HEAD`），与远端同分支最新 hash（`git ls-remote <url> <branch>`）比对：
>    - **hash 相同** → 远端无变更，**不拉取**，直接复用 `current` 下原代码目录，记录"命中缓存未拉取"。
>    - **hash 不同** → 远端有更新，**执行拉取**，在 `backup` 目录 clone（或 `git fetch` 增量拉取）取最新代码。
> 3. 若**不存在**（首次拉取）→ 直接执行拉取。
> 4. 复用或拉取完成后，`containsRegularFile` 校验与 `Files.move` 原子替换逻辑保持不变。
>

**Step 4：失败处理**

| 失败场景 | 处理方式 | 异常码 |
| --- | --- | --- |
| 快照目录越界 | 直接抛业务异常，不做目录操作 | `30020` |
| Git 地址为空 | 抛"Git仓库地址为空：{项目名}"，外层 `safeDelete(backup)` 清理 | 包装为 `30021` |
| clone 失败 / 认证失败 / 网络异常 | 异常冒泡至 `prepare` 的 catch，`safeDelete(backup)` 清理本次临时目录，抛"扫描源准备失败：{原因}" | `30021` |
| 拉取目录无普通文件 | 抛"扫描源中没有可扫描文件"，同上清理 | 包装为 `30021` |

**快照层失败承接（`TaskService.createSnapshotAndManifest`）**：

- `prepare` 抛出的异常被捕获：先执行 `jdbc.update` 将 `scan_task` 置为 `manifest_status='FAILED'`、`status='DRAFT'`、写入截断后的 `error_message`（`limit(msg, 1800)`）。
- 再**重新抛出**原异常，事务回滚，任务回到草稿态，可修改后重试；已产生的 `backup` 临时目录由 `SourceWorkspaceService` 清理，不留脏数据。

**涉及的核心方法与集合汇总**：

| 层次 | 类 | 关键方法 | 操作的集合 / 结构 |
| --- | --- | --- | --- |
| Service | `SourceWorkspaceService` | `prepare` | 目录路径 `base/backup/current`；异常清理 |
| Service | `SourceWorkspaceService` | `prepareCode` | `sourceType` 分支（`GIT`/`UPLOAD`） |
| Service | `SourceWorkspaceService` | `cloneRepositories` | `List<GitProject> projects`、`Set<String> directories` |
| Service | `SourceWorkspaceService` | `cloneRepository` | `CloneCommand`（JGit） |
| Service | `TaskService` | `createSnapshotAndManifest` | 快照事务、失败状态回写 |



**分层调用关系**：

| 层次 | 类/接口 | 关键方法 | 说明 |
| --- | --- | --- | --- |
| Controller | `RepositoryController` | `create` | REST 入口，接收并校验入参后转调 Service |
| Service | `RepositoryService` | `create` / `prepare` / `prepareGit` | 校验代码库与分支，装配 Git 项目清单 JSON，设置审计字段 |
| Mapper | `RepositoryMapper` | `insert` | 数据写入 |

**逻辑要点**：

1. 校验 `repositoryCatalogIds` 非空且 ≤100 个，各代码库须对当前用户可访问。
2. 校验 `defaultBranch` 非空且匹配 `^[A-Za-z0-9._/-]{1,128}$`（不含 `..`、不以 `/` 开头结尾）。
3. 将选中的代码库组装为 `gitProjectsJson`（含项目 ID、名称、URL、应用），写入 `repositoryName`（`名称@分支`）、`repositoryCode`、`repositoryUrl`。
4. `scanSourceType` 设为 `CODE`；`enabled` 缺省为 `true`；写入操作人审计字段。
5. 调用 `RepositoryMapper.insert` 落库，返回新扫描源 ID。

#### 2.2.4.2 ZIP 上传（UPLOAD）

**处理流程**：

`RepositoryView` 前端保存 → `RepositoryController.create` → `RepositoryService.create` → `prepare` → `prepareUpload` → `RepositoryMapper.insert`；保存成功后 → `RepositoryController.upload(id, file)` → `RepositoryService.upload` → `RepositoryMapper.updateFile`。

**分层调用关系**：

| 层次 | 类/接口 | 关键方法 | 说明 |
| --- | --- | --- | --- |
| Controller | `RepositoryController` | `create` / `upload` | 创建入口 + 文件上传入口 |
| Service | `RepositoryService` | `create` / `prepare` / `prepareUpload` / `upload` | 绑定单项目、保存文件、更新存储字段 |
| Mapper | `RepositoryMapper` | `insert` / `updateFile` | 数据写入 / 更新存储标识与文件名 |

**逻辑要点**：

1. 创建时校验已选择单个项目（`repositoryCatalogId`），绑定项目应用，`scanSourceType` 设为 `CODE`，`repositoryName` 设为 `ZIP@项目名`。
2. 创建成功后调用上传接口：校验仅 UPLOAD 可上传、文件非空、扩展名为 `.zip`。
3. 文件名安全化处理，以随机 UUID 生成存储文件名存入 `storageKey`，记录 `originalFileName`，调用 `updateFile` 更新。
4. `enabled` 缺省为 `true`；写入操作人审计字段。

**ZIP 上传执行细节**：

ZIP 流程分两阶段：**① 文件上传落盘**（`RepositoryService.upload`，创建扫描源后执行）；**② 快照生成时解压**（`SourceWorkspaceService.prepareCode` + `ZipExtractor`，任务建快照时执行）。

**阶段①：上传落盘（`RepositoryService.upload(Long id, MultipartFile file)`）**

- 前置校验（`prepare` / `upload` 内）：
  - `sourceType` 必须为 `UPLOAD`，否则抛 `20007`（"只有ZIP扫描源允许上传文件"）。
  - 文件非空，否则抛 `20003`。
  - 原始文件名 `getOriginalFilename()` 安全化（`safeName` → `Paths.get(name).getFileName()`，去路径仅取文件名），后缀必须为 `.zip`（不区分大小写），否则抛 `20008`。
- 存储：
  - `Files.createDirectories(root)` 确保 `storageRoot` 存在；生成随机文件名 `UUID.randomUUID() + ".zip"` 作为 `storageKey`。
  - 目标路径 `target = root.resolve(name).normalize()`，校验 `target.startsWith(root)` 防路径越界，否则抛 `20004`。
  - `file.transferTo(target.toFile())` 落盘。
  - `mapper.updateFile(id, name, originalFileName)` 将 `storage_key`、`original_file_name` 写库。
- 异常：`BusinessException` 原样抛出；其它异常包装为 `20005`（"文件保存失败"）。

**阶段②：快照解压（`SourceWorkspaceService.prepareCode` + `ZipExtractor.extract`）**

- `prepareCode` 中，当 `sourceType=UPLOAD` 时：
  - 校验 `storageKey` 非空，否则抛"ZIP扫描源尚未上传文件"。
  - 定位 `zip = storageRoot.resolve(storageKey).normalize()`，校验 `zip.startsWith(storageRoot)` 且 `Files.isRegularFile(zip)`，否则抛"ZIP源文件不存在"。
  - 调用 `ZipExtractor.extract(zip, target)` 安全解压到 `backup` 目录。
- `ZipExtractor.extract` 安全解压（核心）：
  - **编码检测 `detectCharset`**：先用 `UTF-8` 遍历校验所有条目名（`validateNames`），若抛 `IllegalArgumentException` 则改用 `GBK`（兼容 Windows 中文环境常见的中文文件名）。
  - **条目数上限** `MAX_ENTRIES = 10000`：每读一个条目 `++count` 超限抛"压缩包文件数量超限"（防 ZIP 炸弹）。
  - **解压体积上限** `MAX_EXPANDED_SIZE = 500MB`：边写边累计 `total`，超限抛"压缩包解压大小超限"。
  - **路径越界防护**：对每个条目 `target = root.resolve(entry.getName()).normalize()`，校验 `target.startsWith(root)`，否则抛"压缩包包含非法路径"（防 `../` 路径穿越）。
  - 目录条目 `Files.createDirectories(target)`；普通文件先建父目录再以 8KB 缓冲流写盘。
  - `IllegalArgumentException` 包装为"ZIP文件名编码不受支持，请使用UTF-8或GBK编码重新压缩"。

**失败处理**：

| 失败场景 | 处理方式 | 异常码 |
| --- | --- | --- |
| 非 UPLOAD 源上传 | 拒绝，抛"只有ZIP扫描源允许上传文件" | `20007` |
| 上传文件为空 | 抛"上传文件为空" | `20003` |
| 非 `.zip` 后缀 | 抛"资源文件必须为ZIP格式" | `20008` |
| 存储路径越界 | 抛"非法文件路径" | `20004` |

- **处理步骤**：
  1. **查询需求子条目**：前端选择应用与版本号后，后端调用 e企研接口（`【待确认】` 接口地址，建议 `GET ip:端口/...`）按 `application + versionNo` 查询需求子条目列表（子条目编号 `subitem_no`）。

  3. **无结果兜底（浏览器下载）**：若 `doc_info` 无查询结果，前端自动弹窗  到 e企研网址 `ip:端口/subitemDesign`（`【待确认】` 实际域名/端口与参数拼接），用户在该窗口内手动下载详细设计文档后上传。
  4. **上传入库**：下载得到文档后，用户按「阶段② 文档上传」流程调用 `upload(id, file, docType=DETAIL)` 上传；后端保存 `storageKey` 与 `originalFileName`。
- **doc_info 表查询要点**：
  - 过滤条件：`user_id`（统一认证编号）+ 子条目/条目编号 + `valid=1`；`create_time` 用于版本排序，取最新。
  - 返回内容：`content`（正文）作为文档正文；`subitem_no` / `concept_no` / `item_no` 用于标识与排序。
  - 合并策略：多个子条目按 `subitem_no` 顺序拼接为「详细设计.md」一份文档。
- **失败处理**：
  | 失败场景 | 处理方式 |
  | --- | --- |
  | e企研接口异常 / 超时 | 抛"详细设计需求子条目查询失败"（`【待确认】` 异常码） |
  | doc_info 无结果 | 前端弹 iframe 窗口 `ip:端口/subitemDesign` 由用户下载后上传 |
  | 用户未上传 | 扫描源保存成功但未上传详细设计文档时，`prepareMd` 落盘报"缺少详细设计文档" |
- **待确认清单**：e企研需求子条目接口地址与出入参；doc_info 表所在数据源连接配置；`subitemDesign` 完整 URL 与参数；e企研鉴权方式（如 UCID token）。

- 选择应用（`application`，appID）。

## 2.3 扫描任务与扫描结果

> 说明：前端菜单该模块为「扫描任务」与「扫描结果」两个页签（`TaskView.vue`，路由 `/tasks`；其中 `/results` 重定向到 `/tasks?tab=results`）。本章描述任务全生命周期与结果汇总；问题清单（`/issues`）见 2.4。

### 2.3.1 详细设计

**功能定位**：选择扫描源与同类型规则创建扫描任务，执行时固化规则、扫描源参数与提示词为不可变快照，并生成扫描文件清单（manifest）；支持异步执行、进度展示、暂停、继续、放弃与删除，并**支持设置定时启动**（按 cron 表达式周期触发，到点自动入队执行）；执行完成后按任务汇总扫描结果（文件数、问题数与风险分级）。核心特点：**快照与清单不可变、断点续扫、状态可回溯**。

**核心概念**：

- **任务类型 `taskType`**：`NORMAL`（普通规则，关键字/正则匹配）/ `AI`（大模型两阶段研判）；同一任务只能选择同类型规则。
- **扫描内容 `scanSourceType`**：`CODE`（Git/ZIP 代码）/ `MD`（HTTP MD 文档）。
- **任务快照 `task_snapshot`**：任务保存时固化任务名、描述、类型、扫描源快照、应用版本、扫描路径、文件类型、排除路径、提示词快照，并计算 `snapshot_hash`；每保存一次生成新版本。
- **扫描清单 `task_scan_manifest`**：基于快照目录遍历生成待扫描文件列表（含相对路径、类型、大小、SHA-256 内容摘要），并计算整体 `manifest_hash`，执行前需校验清单未失效。
- **执行单元 `task_execution_unit`**：运行时的最小粒度，一个「文件 × 规则」组合对应一个单元，含阶段（初始 stage：`NORMAL_MATCH` 普通 / `AI_CHECK` CODE+AI / `MD_CHECK` MD）、状态、租约（lease）与结果提交键（`result_commit_key`），支持断点续扫、AI 重试与幂等提交。

**任务状态机**（`scan_task.status`）：

`DRAFT`（草稿）→ `READY`（清单就绪）→ `QUEUED`（排队）→ `RUNNING`（执行中）→ `SUCCESS` / `PARTIAL_SUCCESS` / `FAILED`（结束）；另有中间态 `STOP_REQUESTED`（停止请求中）→ `PAUSED`（已暂停）→ 可 `QUEUED`（继续）/ `ABORTED`（放弃）；`DELETE` 删除后为 `DELETED`。

**处理流程（新建任务）**：

`TaskView` 前端保存 → `TaskController.create(TaskCreateDTO)` → `TaskService.create` → `validate`（校验扫描源与规则）→ `insertSnapshot`（写快照）→ 写 `task_snapshot_rule` → `workspaceService.prepare`（Git/ZIP/MD 拉取落地）→ `generateManifest`（生成清单）→ 任务置 `READY`。若 `executeImmediately=true` 则 `execute` 直接入队执行。

**执行流程（启动任务）**：

`TaskView` 前端点"启动" → `TaskController.execute(id)` → `TaskService.execute` → `verifyManifest`（校验清单摘要）→ `insertRun`（写运行）→ `createExecutionUnits`（生成 文件×规则 单元）→ `publishAfterCommit` 发布 `TaskQueuedEvent` → 事务提交后 `ScanTaskExecutor.onQueued` 异步接管 → `execute(runId)` 循环取单元执行 → `refreshProgress` 刷新进度 → `finish` 汇总状态。

**涉及的核心方法（`TaskService`）**：

| 方法 | 作用 | 关键操作 |
| --- | --- | --- |
| `create` / `update` | 新建 / 编辑任务 | `validate` → `insertSnapshot` → `workspaceService.prepare` → `generateManifest` → 置 `READY` |
| `copy` | 复制任务 | 读当前快照的规则 ID 与范围，重新走 `create` 生成独立快照 |
| `regenerateManifest` | 重新生成清单 | 基于当前快照重新 `generateManifest`（增量版本号） |
| `execute` | 启动运行 | `verifyManifest` → `insertRun` → `createExecutionUnits` → 发布事件 |
| `stop` / `resume` / `abort` | 停止 / 继续 / 放弃 | `stop`、`resume` 更新状态后 `publishAfterCommit` 发布事件；`abort` 仅更新状态不发布事件 |
| `createSnapshotAndManifest` | 快照 + 清单生成 | 组装 `snapshot_hash`、固化规则快照、拉取源、生成清单 |
| `generateManifest` | 生成扫描清单 | 遍历 `serverRootPath` 下文件，过滤排除/类型，写入清单与 SHA-256 摘要 |
| `verifyManifest` | 校验清单有效性 | 逐文件重算 SHA-256 与整体 `manifest_hash` 比对 |
| `createExecutionUnits` | 生成执行单元 | 文件 × 规则 笛卡尔积，生成 `result_commit_key` |

**涉及的集合与数据结构**：

- `SUPPORTED_TYPES`：支持的文件类型集合（java/js/ts/vue/xml/yml/yaml/json/md/txt/sql/properties/html/css/py/sh）。

> /docx/pdf 暂搁置

- `normalizedPaths`：用 `LinkedHashSet` 去重、路径安全化（防 `..`、绝对路径），默认 `"."`。
- `normalizedTypes`：用 `LinkedHashSet` 去重、`retainAll(SUPPORTED_TYPES)` 交集过滤，空则默认全部；交集后为空抛 `30037`。
- `normalizedExcludes`：默认排除 `.git`、`node_modules`、`target` 并入用户排除项。
- `generateManifest`：用 `TreeSet<Path>` 收集待扫描文件（按路径排序去重）、`MessageDigest SHA-256` 计算内容摘要与整体 `manifest_hash`。
- `createExecutionUnits`：双重 `for` 文件 × 规则，`sha256(runId:file:rule:0:stage)` 生成 `result_commit_key`（幂等键）。

**执行器 `ScanTaskExecutor`**：

- **事件驱动**：`@Async @EventListener` 监听 `TaskQueuedEvent`；`@EventListener(ApplicationReadyEvent)` 启动时先 `recoverExpiredWork` 再恢复遗留 `QUEUED` 运行；`@Scheduled(fixedDelay=60000)` 每分钟 `recoverExpiredWork`：将超时（>5 分钟）的单元租约置回 `PENDING` 清租约，并将 `RUNNING/STOP_REQUESTED` 且超时的运行按 `stop_requested` 置回 `QUEUED`（继续，**重发事件**）/ `PAUSED`（停止请求，不发事件）。
- **运行抢占 `execute`**：先 `UPDATE scan_task_run SET status='RUNNING' WHERE status='QUEUED'` 抢占，`changed != 1` 直接 return（防多实例重复执行）；随后建 `RunContext`、置任务 `RUNNING`、`ensureResult` 建/取 `scan_result`，再循环 `nextUnit → process → refreshProgress`。
- **单元租约与重试 `nextUnit`**：取一条 `PENDING` 单元（AI 任务同时取 `FAILED` 且 `retry_count < tokenRetryCount` 的可重试单元），写入 `lease_id` + `lease_expire_time`（5 分钟）并 CAS 抢占；租约保证多实例/崩溃后可恢复，`retry_count` 上限由 Token 重试次数控制。
- **单元执行 `process`**：先校验文件路径越界 + `contentHash` 与清单一致（文件变化则失败）；`NORMAL` 走 `scanNormal`，`AI` 走 `scanWithAi`；成功置 `SUCCESS` 清租约，失败置 `FAILED` 且 `retry_count+1` 并写错误。
- **普通扫描 `scanNormal`**：先 `stripComments` 按语言去注释，再按 `KEYWORD`（`Pattern.quote` 子串）或 `REGEX` 匹配，逐行 `Matcher.find`，命中年限 `10000`。
- **AI 扫描 `scanWithAi`**：`waitForCredential`（轮询最多 120 秒）获取凭证，CODE 先取 `preliminary_result`（空则用 `AI_CHECK` 提示词检查并 `validateModelJson`，落 `preliminary_result`），再以 `AI_RESULT_UPDATE` 提示词生成最终结果；MD 直接用 `MD_CHECK`；`validateModelJson` 解析 `issues` 数组，`insertIssue` 以 `result_commit_key:index` 幂等写入 `scan_issue`；`finally` 中 `releaseCredential` 释放凭证。
- **进度刷新 `refreshProgress`**：统计单元成功/失败、文件完成/成功/失败、问题数（含 HIGH/MEDIUM/LOW/INFO 分级），回写 `scan_task_run`、`scan_task` 与 `scan_result` 汇总。
- **结束判定 `finish`**：先 `refreshProgress` 收尾，再按失败单元数：0 → `SUCCESS`；成功为 0 → `FAILED`；否则 `PARTIAL_SUCCESS`。
- **暂停 `pause`**：运行与任务置 `PAUSED`，保留已产生结果。
- **文件解析 `parse`**：`docx` 用 `XWPFDocument` 提取段落、`pdf` 用 `PDFTextStripper`、**普通文本文件**按 UTF-8 读取且单文件超 10MB 抛异常（docx/pdf 无大小限制）。

- **文件读取与重试机制**：见 **2.3.2.6「文件读取与重试机制」**——AI 文件读取采用「递归生成目录树 → 逐文件作为进度 → AI 读取 → 失败行号续读/间隔重试 → 成功落库 → 汇总上下文 → 统计字符与 token」共 8 个环节，其中**行号续读、间隔重试、跨文件上下文汇总、字符/token 统计为设计目标，当前未实现（后期开发）**。

### 2.3.2 重要接口

#### 2.3.2.1 接口设计

任务中心负责扫描任务的全生命周期管理：任务创建时固化规则、扫描源参数与提示词为不可变快照，并生成扫描文件清单；启动后异步执行，支持暂停、继续、放弃与断点续扫；提供快照历史、清单预览与执行单元的可追溯查询。

| 校验项 | 规则 | 异常码 |

#### 2.3.2.6 业务逻辑处理（核心方法执行细节）

**快照与清单生成（`createSnapshotAndManifest`）**：

1. `nextSnapshotVersion` 计算下一快照版本号；`promptSnapshot` 按类型装配 AI 提示词。
2. 组装 `hashContent`（任务类型、扫描内容、仓库、版本、路径、类型、排除、规则、提示词），`sha256Json` 生成 `snapshot_hash`；`insertSnapshot` 落库快照。
3. 循环写 `task_snapshot_rule`（固化每条规则的完整快照）。
4. `workspaceService.prepare` 拉取/落地代码或文档到快照目录，回写 `server_root_path`。
5. `generateManifest` 遍历生成清单，任务置 `manifest_status='READY'`、`status='READY'`。
6. 失败：置 `manifest_status='FAILED'`、`status='DRAFT'`、写 `error_message`，重抛异常回滚。

**清单生成（`generateManifest`）**：

1. 版本号自增，`insertManifest` 落库（`BUILDING`）。
2. 遍历配置路径 `paths`（`.root` 起），`Files.walk` 过滤普通文件，计算相对路径、扩展名类型。
3. `excluded`（排除目录/路径匹配）或类型不在支持集 → `excluded_count` 累计；否则加入 `TreeSet<Path>` 去重。
4. 对每个文件计算 SHA-256 摘要，`manifestDigest.update(相对路径:hash)`，写入清单文件表。
5. 聚合整体 `manifest_hash`，清单置 `READY`，回写文件数、排除数、总大小。

**运行启动（`execute`）**：

1. `ensureNoOpenRun` 校验无运行中；取当前清单并校验 `status='READY'`（否则抛 `30025`），再 `verifyManifest` 校验清单（逐文件重算 SHA-256 + 整体摘要比对，失效抛 `30031`）。
2. AI 任务校验可用凭证数（`availableCredentialCount==0` 抛 `30026`）。
3. `insertRun` 写 `scan_task_run`（`QUEUED`），生成 `run_no`。
4. `createExecutionUnits`：遍历清单文件 × 快照规则，生成执行单元，初始 `stage` 按类型取 `NORMAL_MATCH` / `MD_CHECK` / `AI_CHECK`，`result_commit_key = sha256(runId:file:rule:0:stage)`（幂等）。
5. 更新运行单元总数与任务状态（`QUEUED`）、清零进度统计，`publishAfterCommit` 事务提交后发事件。

**异步执行（`ScanTaskExecutor.execute`）**：

1. 抢占运行：`QUEUED → RUNNING`，失败则直接返回（避免重复执行）。
2. 加载 `RunContext`，`ensureResult` 建/取 `scan_result`。
3. 循环：`nextUnit` 取单元并加租约 → `process` 执行 → `refreshProgress` 刷新进度；遇 `STOP_REQUESTED` 则 `pause`。
4. `finish`：无失败 `SUCCESS`、全失败 `FAILED`、否则 `PARTIAL_SUCCESS`。
5. 异常兜底：运行与任务置 `FAILED`、写 `error_message`。

**单元执行（`process`）**：

- 校验文件路径越界 + `contentHash` 一致（防文件变更）。
- `NORMAL` → `scanNormal`（去注释 → 关键字/正则逐行匹配 → `insertIssue`）。
- `AI` → `scanWithAi`（获取凭证 → 两阶段/MD 调用 → 解析 issues → 幂等落库）。
- 成功：单元置 `SUCCESS`、清租约；失败：`FAILED`、`retry_count+1`、写错误（AI 可重试 `tokenRetryCount` 次）。

**文件读取与重试机制（设计目标，部分未实现，后期开发）**：

> 说明：以下为规划中的 AI 文件读取与断点续读机制，作为单元执行的整体流程，**当前版本仅实现其中基础部分**，未实现项均已标注。

整体流程共 8 个环节：

1. **递归生成目录树**（已实现）：清单阶段 `generateManifest` 用 `Files.walk` 递归遍历快照目录，生成待扫描文件列表（相对路径、类型、大小、SHA-256）。
2. **逐项目逐文件作为任务进度**（已实现）：任务启动后 `execute → nextUnit` 按「文件 × 规则」逐单元执行，`refreshProgress` 按文件完成数刷新进度。
3. **每个文件 AI 读取**（已实现，但为整文件一次性）：`scanWithAi` 对每个文件调用模型（CODE 两阶段 / MD 单阶段）；**当前整文件一次性提交，并截断为前 `maxContentLength=30000` 字符，超出部分丢弃**。
4. **失败记录行号、从失败行号续读**（**未实现**）：当前重试是**整个文件从头重新 AI 读取**，未按行号分段续读。规划目标：读取失败时记录**失败行号**，下次重试从该失败行号处继续读取，跳过已成功段落。
5. **失败后间隔重试、最大三次**（部分未实现）：当前有次数上限重试（`retry_count < tokenRetryCount`，默认 3），但**无"失败后间隔 N 秒再重试"**。规划目标：失败后间隔固定秒数再重试，单文件最多重试 **3 次**。
6. **每文件成功后读结果存库**（已实现）：`scanWithAi` 解析出 `issues` 数组后，`insertIssue` 以 `result_commit_key:index` 幂等写入 `scan_issue`。
7. **最终汇总所有结果**（部分实现）：运行结束 `refreshResult` 聚合统计各风险分级写入 `scan_result`；规划目标为**重新开启一个上下文，把所有文件的读取结果一并提交汇总**（当前为聚合统计，未做跨文件上下文汇总）。
8. **每次请求计算字符串总数与 token 个数**（**未实现**）：当前 `AiModelHttpClient.invoke` 不统计字符数、不估算 token 数、也不落库。规划目标：每次 AI 请求计算 `content` 的**字符数/字符串总数**与 **token 个数**，并记录保存。

**暂停 / 继续 / 放弃**：

- `stop`：`QUEUED` → 运行与任务置 `PAUSED`；`RUNNING` → 置 `STOP_REQUESTED`，执行器下轮 `pause`。
- `resume`：仅 `PAUSED` 可继续，运行置 `QUEUED`、`resume_count+1`，重新发布事件续扫（断点续扫）。
- `abort`：仅 `PAUSED` 可放弃，运行与任务置 `ABORTED`，保留已产生结果。

**前端交互（`TaskView.vue`）**：

- 任务列表每 4 秒轮询刷新进度（`timer`），`percent` 按完成文件数计算。
- 列表操作按钮按状态动态显示：`QUEUED/RUNNING` 可"停止"，`PAUSED` 可"继续/放弃"。
- 新建/编辑表单含任务名、扫描源、规则（同类型校验）、扫描路径、文件类型、排除路径、描述、生成后启动。
- 详情弹窗展示任务信息与快照历史；清单预览弹窗展示清单摘要、文件列表、支持"重新生成"。
- 编辑保存会提示"生成新快照，请重新选择同类型规则"。

#### 2.3.2.7 核心流程（三种扫描源完整流程）

三种扫描源（Git 代码库 / ZIP 代码包 / 文档接口）并非只是"数据源不同"，而是从**数据形态、获取方式、安全校验、规则适用、扫描语义、结果类型**六个维度都有本质区别。一次扫描任务都经历 6 个阶段：**① 准备内容 → ② 固化快照 → ③ 生成清单 → ④ 启动运行 → ⑤ 逐单元扫描 → ⑥ 结果产出**，其中"准备内容"因扫描源而异，其余完全统一。

**三种扫描源的本质区别**：

| 维度 | Git 代码库 | ZIP 代码包 | 文档接口 |
| --- | --- | --- | --- |
| **数据形态** | 文本源码（按目录树组织） | 文本源码（压缩包解开后是目录树） | 设计文档（Markdown/文本列表） |
| **获取方式** | 远程 `git clone` 拉分支 | 本地上传 `.zip` 安全解压 | 外部 HTTP 接口拉取 |
| **是否需要网络** | 需要（拉远程仓库） | 不需要（本地文件） | 需要（调用外部服务） |
| **是否用户本地上传** | 否 | **是**（文件由人上传） | 否 |
| **校验重点** | 分支存在、认证、目录越界 | 压缩包数量/大小/编码/路径（防炸弹、防穿越） | 版本格式、文档数量/单篇大小/文件名/编码 |
| **规则适用** | 普通规则 + AI 规则 | 普通规则 + AI 规则 | **仅 AI 规则** |
| **扫描语义** | 逐行匹配代码（关键字/正则）或 AI 研判 | 同左 | **仅 AI 研判**（文档无关键字/正则语义） |
| **AI 提示词阶段** | 两阶段（检查→结果更新） | 两阶段（检查→结果更新） | **单阶段（MD 检查）** |
| **大小上限** | 单文件 10MB | 解压总量 500MB / 条目 10000 | 单文档 50MB / 总数 10000 |
| **清单来源** | 代码目录树 | 代码目录树 | 文档列表（非目录树） |
| **上下文计数** | 每单元统计字符串/token | 每单元统计字符串/token | 每单元统计字符串/token |

> 一句话总结：**Git 是"拉远程代码"、ZIP 是"解本地压缩包"、文档是"拉接口文档"**；前两者扫描的是"代码"（可普通匹配、可 AI），后者扫描的是"文档"（**只能 AI**）。

**统一流程（三种来源相同）**：

1. 准备内容（差异点：见各扫描源）
2. 固化快照（锁定扫描源、规则、提示词，不可变）
3. 生成清单（遍历生成待扫描文件/文档列表 + 摘要）
4. 启动运行（校验清单与凭证 → 生成执行单元）
5. 逐单元扫描（普通匹配 / AI 研判 → 问题落库）
6. 结果产出（分级汇总 → 问题清单 → 人工处理 → 导出）

1. **固化快照**：任务保存时把本次选择固化为不可变快照：任务信息、扫描源、应用版本、扫描路径/文件类型/排除路径、规则快照、AI 提示词。修改扫描源或规则不影响已保存任务，保证可回溯。
2. **生成清单**：在快照目录下递归遍历文件/文档，按排除路径、类型过滤，计算内容 SHA-256 摘要，生成"待扫描清单"与整体摘要（`manifest_hash`）。
3. **启动运行**：校验清单就绪且摘要未失效；AI 任务校验凭证充足；生成执行单元（文件×规则）。
4. **逐单元扫描 → 落库 → 汇总**，每个执行单元（文件 × 规则）的完整执行过程：
   1. **取单元**：取出一个待执行单元，加租约标记（防重复、可恢复）。
   2. **加载规则**：读取该单元对应规则的完整配置（普通规则的关键字/正则/风险等级；AI 规则的提示词/JSON Schema）。
   3. **组上下文**：普通规则按语言去注释后逐行匹配；AI 规则把**文件内容 + 提示词 + 上下文**组装成发给模型的请求上下文。
   4. **计算上下文规模（设计目标，当前未实现）**：每次 AI 请求前，计算组装好的请求上下文的**字符串总大小（字符数）**与**预估 token 数量**，并随调用记录保存。**注：当前版本未实现该统计，属后期开发项。**
   5. **执行并读取行号**：扫描过程中记录每个问题出现的**起止行号**——
      - **普通规则**：对文件逐行（`i` 从 0 开始）做关键字/正则匹配，命中即记录当前行号（`startLine=endLine=i+1`），即问题出现的具体行。
      - **AI 规则**：模型返回的问题列表带 `startLine` / `endLine` 字段，解析并记录问题在文件中的起止行号（起始行至少为 1，结束行不小于起始行）。
   6. **落库**：产出的问题连同**文件路径、起止行号**以「文件×规则×序号」幂等写入问题表（`start_line` / `end_line`），供问题清单定位与跳转。
   7. **进度**：刷新已完成文件数、成功/失败文件数、问题数。

> 统一抽象：**文件/文档清单 → 文件×规则执行单元（组上下文 → 统计字符串/token → 执行并读取行号 → 落库） → 问题明细 → 结果汇总**。

**扫描源一：Git 代码库流程**——扫描"代码"，数据源是远程 Git 仓库，核心是联网克隆分支代码，支持普通 + AI 规则。

```
[配置代码库] 代码库目录(名称/地址/应用) + 分支
        ↓
[创建任务] 选 Git 扫描源 + 同类型规则（普通/AI 均可）
        ↓
【准备内容】cloneRepositories：读取 Git 项目列表 → 校验地址非空、目录安全化防重名 → 按 defaultBranch git clone 到快照目录
        ↓
[固化快照] [生成清单] [启动运行]
        ↓
[逐单元扫描] 组上下文 → 统计字符串/token → 普通匹配 / AI 两阶段研判 → 记录问题行号
        ↓
[结果落库] 问题连同行号幂等落库 → 分级汇总
```

- **与其它方式差异**：**多项目支持**（一个扫描源可配多个 Git 项目，各自克隆独立子目录）；**可选认证**（配账号口令否则匿名）；**分支**（按 `defaultBranch`）。
- **失败处理**：地址为空、克隆/认证失败 → 清理临时目录，任务回草稿；快照目录越界抛 `30020` 拒绝。

**扫描源二：ZIP 代码包流程**——扫描"代码"，数据源是用户本地上传的 `.zip` 压缩包，核心是**由人上传、系统安全解压**。与 Git 一样支持普通 + AI 规则，但不联网、无分支、无多项目。

```
[创建扫描源] ZIP 扫描源（绑定一个项目应用）
        ↓
[上传压缩包] 上传 .zip → 安全落盘 → 记录 storageKey + 原文件名
        ↓
[创建任务] 选 ZIP 扫描源 + 同类型规则（普通/AI 均可）
        ↓
【准备内容】prepareCode → ZipExtractor.extract：校验 storageKey 非空 → 定位压缩包、校验路径在 storageRoot 内 → 安全解压到快照目录
        ↓
[固化快照] [生成清单] [启动运行] [逐单元扫描] [结果落库]（同统一流程）
```

- **安全解压（ZIP 特有）**：
  | 校验 | 说明 |
  | --- | --- |
  | 文件数量上限 | 条目数 > 10000 拒绝（防 ZIP 炸弹） |
  | 解压总量上限 | 解压后总大小 > 500MB 拒绝（防压缩比炸弹） |
  | 路径越级 | 每个条目路径须在目标目录内（拦截 `..`） |
  | 编码兼容 | 先 UTF-8，失败回退 GBK（兼容中文文件名） |

  这是三种方式中**唯一需要"解压"**的扫描源，也是安全校验最重的——因为压缩包内容不可信。
- **失败处理**：未上传 ZIP 就建任务、文件非 `.zip`、解压超限、路径非法、编码不支持 → 回草稿并提示。

**扫描源三：文档接口流程**——扫描"文档"（概要/详细设计），数据源是外部文档服务的 HTTP 接口，核心是**调用外部接口拉取版本文档、且只能 AI 研判**。

```
[创建扫描源] 文档类型(概要/详细) + 应用 + 版本(YYYYMM)
        ↓
[校验版本] 调用版本查询接口，确认版本可选
        ↓
[创建任务] 选文档扫描源 → 仅可选 AI 规则
        ↓
【准备内容】prepareMd → mdClient.download：校验文档类型合法、应用非空、版本为 YYYYMM → 按 应用+版本 调用文档接口 → 拉取该版本全部文档逐篇落盘（按序号命名）
        ↓
[固化快照] [生成清单] [启动运行] [逐单元扫描] [结果落库]（同统一流程）
```

- **与其它方式差异**：
  - **规则类型**：文档**只能选 AI 规则**（无"关键字/正则逐行匹配"语义），是与 Git/ZIP 最大区别。
  - **清单来源**：Git/ZIP 生成的是**代码目录树**，文档生成的是**文档列表**（非目录树）。
  - **AI 阶段**：代码 AI 走**两阶段**（`AI_CHECK` → `AI_RESULT_UPDATE`）；文档 AI 走**单阶段**（`MD_CHECK`）。
  - **版本维度**：按应用+版本（`YYYYMM`）拉取，Git/ZIP 无版本概念。
  - **上下文计数**：文档 AI 调用同样在每单元统计字符串大小与预估 token 数量（设计目标，当前未实现），与代码扫描一致。
- **安全校验**：版本格式须为 `YYYYMM`；文档总数 > 10000 拒绝；单篇 > 50MB 拒绝；文件名安全化；内容兼容 Base64 / 纯文本。
- **失败处理**：版本/文档接口异常、返回空文档、超限 → 回草稿并提示。

**三种扫描源统一对照**：

| 环节 | Git 代码库 | ZIP 代码包 | 文档接口 |
| --- | --- | --- | --- |
| 数据形态 | 代码 | 代码 | **文档** |
| 获取方式 | 远程 clone | 本地解压 | 接口拉取 |
| 是否联网 | 是 | 否 | 是 |
| 用户上传 | 否 | **是** | 否 |
| 分支 | 有（defaultBranch） | 无 | 无 |
| 多项目 | 有 | 无 | 无 |
| 版本 | 无 | 无 | **有（YYYYMM）** |
| 安全解压 | 无 | **有（防炸弹/防穿越/编码）** | 无 |
| 规则适用 | 普通 + AI | 普通 + AI | **仅 AI** |
| AI 阶段 | 两阶段 | 两阶段 | **单阶段 MD** |
| 大小上限 | 单文件 10MB | 总量 500MB/条目10000 | 单篇 50MB/总数10000 |
| 上下文计数 | 每单元统计 | 每单元统计 | 每单元统计 |
| 快照/清单/执行/结果 | 统一 | 统一 | 统一 |

> 差异在"准备内容"，统一在"扫描模型"。统一抽象：**文件/文档清单 → 文件×规则执行单元 → 问题明细 → 结果汇总**。

## 2.4 扫描问题

> 说明：前端菜单该模块为「问题清单」页（`IssueView.vue`，路由 `/issues`，可从"扫描结果"页签点"结果明细"进入）。本章描述问题明细的查询、处理与导出；扫描结果汇总本身已并入 2.3。

### 2.4.1 详细设计

**功能定位**：按任务汇总展示扫描问题（文件位置、行号、命中内容、问题说明、整改建议与处理状态），支持按关键字/风险/状态过滤，提供状态处理（确认/解决/忽略）与 Excel 明细导出，供业务人员人工闭环整改。

**核心概念**：

- **扫描结果 `scan_result`**：一次运行对应一条结果汇总，含扫描/成功/失败文件数、问题总数及 HIGH/MEDIUM/LOW/INFO 各分级计数。
- **扫描问题 `scan_issue`**：规则命中或 AI 研判产生的具体问题，含文件位置、行号、命中内容、问题说明、整改建议与处理状态；`result_commit_key` 保证幂等。
- **处理状态 `status`**：`PENDING`（待处理）/ `CONFIRMED`（已确认）/ `RESOLVED`（已解决）/ `IGNORED`（已忽略）。

**处理流程（结果汇总）**：

`ScanTaskExecutor` 执行过程中 `refreshProgress` → `refreshResult` 统计各风险分级，回写 `scan_result`；问题由 `insertIssue` 实时落库 `scan_issue`。

**处理流程（问题查询与处理）**：

`IssueView` 前端查询 → `ResultController.issues` → `ResultService.issues` → `ResultMapper.issuePage` 分页返回；点"处理" → `ResultController.status` → `ResultService.updateIssue` → `ResultMapper.updateIssue` 更新状态与处理意见。

**处理流程（导出）**：

`IssueView` 前端"导出 Excel" → `ResultController.exportIssues` → `ResultService.exportIssues` 用 POI 生成 `.xlsx` → 返回 `attachment` 下载。

**涉及的核心方法（`ResultService`）**：

| 方法 | 作用 | 关键操作 |
| --- | --- | --- |
| `page` | 结果分页 | `ResultMapper.page` 联表（结果/运行/任务/仓库） |
| `get` | 结果详情 | `findById`；不存在抛 `40001` |
| `issues` | 问题分页 | 按关键字/状态/风险/结果过滤 |
| `issue` | 问题详情 | `findIssue`；不存在抛 `40002` |
| `exportIssues` | Excel 导出 | POI 创建 `XSSFWorkbook`，15 列表头 + 样式 |
| `updateIssue` | 更新处理状态 | 校验状态合法，更新状态/意见/处理人 |

**涉及的数据结构与集合**：

- `ResultMapper.issueExport`：最多导出 50000 条。
- `exportIssues`：`Workbook/XSSFWorkbook`、`Sheet`、`CellStyle`（表头深蓝白字加粗居中、日期格式 `yyyy-mm-dd hh:mm:ss`、长文本自动换行）、冻结首行 + 自动筛选、列宽数组。
- `updateIssue`：状态校验集合 `{"CONFIRMED","RESOLVED","IGNORED","PENDING"}`，处理人写 `"system"`。

### 2.4.2 重要接口

#### 2.4.2.1 接口设计

问题清单模块提供问题明细管理：按关键字/状态/风险/结果过滤查询问题，支持处理状态流转与 Excel 明细导出，实现扫描发现的人工确认、整改与忽略闭环；同时提供扫描结果汇总查询接口（供"扫描任务"页的"扫描结果"页签使用）。

#### 2.4.2.2 接口定义

接口清单：

| 功能 | 方法 | 路径 | 请求参数 | 请求体 | 响应 data | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| 结果分页 | GET | `/api/v1/results` | `keyword`,`pageNum=1`,`pageSize=20` | 无 | `PageResult<ScanResult>` | 结果汇总分页 |
| 结果详情 | GET | `/api/v1/results/{id}` | 路径 `id` | 无 | `ScanResult` | 不存在抛 `40001` |
| 问题分页 | GET | `/api/v1/issues` | `keyword`,`status`,`risk`,`resultId`,`pageNum=1`,`pageSize=20` | 无 | `PageResult<ScanIssue>` | 问题条件分页 |

1. `issue(id)` 校验问题存在。
2. 校验 `status` 在合法集合内，否则抛 `40003`。

## 2.5 模型配置

> 说明：前端菜单该模块为「模型设置」页（`ModelSettingsView.vue`，路由 `/model-settings`），含三个页签：**UCID / Token 凭证池**、**内置提示词（管理员）**、**运行参数（管理员）**。

### 2.5.1 详细设计

**功能定位**：维护 AI 扫描所需的大模型凭证池（UCID/Token）、内置提示词模板（AI_CHECK / AI_RESULT_UPDATE / MD_CHECK）与运行参数（Token 失败重试次数），为 AI 规则扫描提供可并发、可重试、可版本化的模型调用能力。

**核心概念**：

- **模型凭证 `user_model_credential`**：每个用户可配置多条凭证（`credential_name`、`ucid`、`token`），Token 以 **AES-GCM 加密**存储于 `token_ciphertext`，并保留掩码 `token_masked`；凭证有启用开关与运行状态（`AVAILABLE` / `BUSY` / `COOLDOWN` / `INVALID`）。
- **凭证池并发**：启用且有效的凭证数即 AI 扫描 CODE/MD 的共享并发数；执行时 `acquireCredential` 抢占一条可用凭证（加租约），`releaseCredential` 释放。
- **内置提示词 `model_prompt_template`**：三种类型（`AI_CHECK` 检查、`AI_RESULT_UPDATE` 结果更新、`MD_CHECK` MD 检查），按 `prompt_type + version_no` 多版本管理，状态 `DRAFT` / `ACTIVE` / `INACTIVE`，同一类型同时仅一条 `ACTIVE`。
- **运行参数**：Token 失败重试次数（`AI_TOKEN_RETRY_COUNT`，存 `system_setting`），范围 0~10，默认 3，仅管理员可改。

**凭证运行状态机**：

`AVAILABLE`（空闲）→（`acquireCredential`）`BUSY`（租用中）→（`releaseCredential`）`AVAILABLE`；租约 5 分钟过期可被抢占恢复；Token 失效置 `INVALID`；触发限流可 `COOLDOWN`。

**涉及的核心方法（`ModelConfigService`）**：

| 方法 | 作用 | 关键操作 |
| --- | --- | --- |
| `credentials` | 凭证列表 | 按用户查，置空 `token_ciphertext`（不下发密文） |
| `createCredential` | 新增凭证 | 校验 Token 非空；`secretCodec.encrypt` 加密 + `mask` 掩码 |
| `updateCredential` | 编辑凭证 | Token 留空保持原密文；重置运行状态与租约 |
| `deleteCredential` | 删除凭证 | 使用中（`BUSY`）不可删 |
| `credentialStatus` | 启停 | 启用时置 `AVAILABLE` |
| `testCredential` | 连接测试 | `aiClient.invoke` 发最小请求验证，更新 `last_test_time` |
| `acquireCredential` / `releaseCredential` | 租用 / 释放 | 加租约（5 分钟）抢占可用凭证，执行完释放 |
| `availableCredentialCount` | 有效凭证数 | 启用且非 `INVALID` 的凭证数 |
| `prompts` / `activePrompt` | 提示词列表 / 启用版 | 按类型查询；`ACTIVE` 最新版 |
| `createPrompt` / `updatePrompt` | 提示词草稿 | 版本号自增；仅 `DRAFT` 可编辑 |
| `activatePrompt` | 启用提示词 | 同类型旧 `ACTIVE` 置 `INACTIVE`，目标置 `ACTIVE` |
| `tokenRetryCount` / `updateTokenRetryCount` | 运行参数 | 读写 `system_setting`；改参须管理员 |

**涉及的数据结构与安全机制**：

- `SecretCodec`：AES/GCM/NoPadding，密钥由 `scan-center.ai.credential-secret` 经 SHA-256 派生（16 字节），每次加密生成 12 字节随机 IV，密文 = `IV(12) + ciphertext` 再 Base64。
- `mask`：Token ≤8 位返回 `****`，否则 `前4位 + **** + 后4位`。
- `acquireCredential`：查询可用凭证（`AVAILABLE` 或租约过期或 `COOLDOWN` 已过），`ORDER BY last_used_time`（未用优先），逐个 CAS 抢占加租约，成功返回凭证与 `lease_id`。
- `AiModelHttpClient.invoke`：POST 到 `scan-center.ai.url`，请求头带 UCID 与 `Bearer{token}`，体含 `model`、`messages`（system/user）、`temperature=0`、`response_format=json_object`；`extractContent` 从 `choices[0].message.content` / `content` / `data` 解析。
- 前端凭证池 `enabledCount`：启用且 `runtimeStatus !== 'INVALID'` 的条数，即 AI 并发数。

| 凭证归属 | 不存在或无权访问 | `60004` |
| 删除凭证 | 使用中（`BUSY`）不可删 | `60005` |
| 启用提示词 | 未配置 `ACTIVE` 类型 | `60006` |
| 编辑提示词 | 仅 `DRAFT` 可编辑 | `60007` |
| 启用提示词 | 目标不存在 | `60008` |
| 提示词类型 | 必须为三种合法类型之一 | `60009` |
| 重试次数 | 仅管理员；范围 0~10 | `60010` / `60011` |
| 大模型调用 | 未配置 URL 抛 `60001`；调用失败抛 `60002` | `60001` / `60002` |

#### 2.5.2.6 业务逻辑处理

**新增凭证（`createCredential`）**：校验 Token 非空 → `secretCodec.encrypt` 加密 → `mask` 生成掩码 → 插入（`runtime_status='AVAILABLE'`）。

**编辑凭证（`updateCredential`）**：查原凭证 → Token 空则保持原密文/掩码，非空则重新加密 → 更新并重置运行状态与租约；未命中抛 `60004`。

**连接测试（`testCredential`）**：解密 Token → `aiClient.invoke(凭证, 测试提示词, '请返回 {"ok":true}')` 发起最小请求 → 更新 `last_test_time`、置 `AVAILABLE`。

**凭证租用（`acquireCredential`）**：查候选（`AVAILABLE` / 租约过期 / `COOLDOWN` 已过，按 `last_used_time` 排序取 20）→ 逐个 `UPDATE ... WHERE 状态条件` CAS 抢占 → 成功加租约（5 分钟）返回；释放（`releaseCredential`）按 `lease_id` 置 `AVAILABLE`。

**启用提示词（`activatePrompt`）**：同类型现有 `ACTIVE` 置 `INACTIVE` → 目标置 `ACTIVE` 并写操作人。

**前端交互（`ModelSettingsView.vue`）**：

- 凭证池页签：展示启用有效凭证数（AI 并发提示）、凭证表（名称/UCID/掩码/运行状态/最近测试/启用开关），操作含编辑/测试/删除。
- 提示词页签：按类型过滤，展示版本/状态/更新时间/内容，`DRAFT` 可编辑、非 `ACTIVE` 可启用；新建时版本号自增落为草稿。
- 运行参数页签：`el-input-number` 设置 0~10 的重试次数并保存（仅管理员）。
- 凭证/提示词编辑弹窗：凭证含名称、UCID、Token（编辑留空保持原值）、启用；提示词含类型（编辑时锁定）、内容、JSON Schema。

## 2.6 用户管理

> 说明：前端菜单该模块为「用户管理」页（`UserView.vue`，路由 `/users`，`requiresAdmin`），管理平台用户及其所属应用与代码库授权关系。

### 2.6.1 详细设计

**功能定位**：管理系统账号（用户名、姓名、外部用户 ID、角色、应用、说明、启停），并为用户关联其应用下全部已启用代码库，支撑按应用授权的扫描范围控制。

**核心概念**：

- **用户角色 `roleCode`**：`ADMIN`（管理员）/ `USER`（普通用户）；管理员应用固定为 `ALL`。
- **应用 `application`**：合法应用集合 `F-BASE / F-GMO / F-GMRM / F-FMPV / F-EFM / F-SCIS / ALL`（`ApplicationOptions`）。
- **代码库授权**：用户创建/编辑后，`syncRepositories` 自动清空并重建 `user_repository_relation`，关联其应用下全部已启用代码库；`enrich` 查询并回填用户的 `repositoryIds` / `repositoryNames`。

**涉及的核心方法（`UserService`）**：

| 方法 | 作用 | 关键操作 |
| --- | --- | --- |
| `page` | 用户分页 | 按关键字/角色/状态过滤，`enrich` 回填代码库 |

| `create` | 新增用户 | `validate` → `insert` → `syncRepositories` |
| `update` | 编辑用户 | 校验后更新 → `syncRepositories` 重建授权 |
| `status` | 启停 | `updateStatus` |
| `delete` | 删除用户 | 内置 `admin` 不可删；清授权关系 + 逻辑删除 |
| `validate` | 校验 | 用户名格式、角色、应用、唯一性 |
| `syncRepositories` | 同步代码库授权 | 清空 → 按应用关联全部已启用代码库 |
| `enrich` | 回填代码库 | 查询应用下已启用代码库，填 `repositoryIds` / `repositoryNames` |

**涉及的数据结构**：

- `validate`：用户名匹配 `^[A-Za-z][A-Za-z0-9_.-]{2,63}$`（字母开头、3-64 位）；角色集合 `{"ADMIN","USER"}`；应用须在 `ApplicationOptions.VALUES` 内；管理员应用必须 `ALL`；用户名唯一（`countUsername`，区分大小写不敏感）。

- `enrich`：按用户应用查代码库，分别收集 ID 与名称列表回填。
